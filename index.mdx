The REST API is the modern TimeLog API and the one to build against for new integrations. It exposes your organization's data — people, departments, legal entities, projects, time — over ordinary HTTPS with JSON bodies and a personal access token.

## Base URL

Every TimeLog site has its own address, so there is no shared host:

```text
https://app{instance}.timelog.com/{account}/api
```

For a site at `https://app3.timelog.com/acme/`, the base URL is `https://app3.timelog.com/acme/api`. [Authentication](/api-reference/authentication) walks through both parts.

## Three things that differ from most APIs

They account for nearly every failed first attempt.

<AccordionGroup>
  <Accordion title="The base URL is yours, not ours" icon="link">
    There is no `api.timelog.com` to call. The host carries your instance number and the path carries your account name, and both come from the address you already use to sign in.
  </Accordion>

  <Accordion title="A token is a whole user, not a scope" icon="key">
    A personal access token acts as the user who created it and carries exactly that user's permissions. There is no narrower scope — a token made from an administrator account is an administrator credential.
  </Accordion>

  <Accordion title="Responses are enveloped" icon="box-open">
    The resource is never at the top level of the body. A single resource arrives under `Properties`, a collection under `Entities[].Properties`, each alongside `Links` and `Actions`. See [Response format](/api-reference/response-format).
  </Accordion>
</AccordionGroup>

## Versions

`v1` and `v2` are both live and both current. They are not two generations of one API: the version sits in the path, and most services exist at only one of the two, so the version is decided per endpoint rather than globally. Each operation page states its own path.

`GET /v1/user/me` and `GET /v2/users/me` are the clearest example — both current, both returning the signed-in user, with different models. Neither supersedes the other.
