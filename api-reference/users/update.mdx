```http
PUT /v1/user
```

Updates an existing user. The user being updated is identified inside the body, not in
the path — this endpoint shares its path with
[Get all users](/api-reference/users/list) and differs only by method.

<Warning>
  **The request model is not specified in the API contract.** `UserUpdateModel` exposes no
  documented fields, so the exact payload this endpoint accepts cannot be stated here.

  In practice it is the user model — see
  [Create a user](/api-reference/users/create#body) for the field list — with `UserId`
  identifying the target. Verify against a sandbox site before putting this in
  production.
</Warning>

## Authorization

<ParamField header="Authorization" type="string" required>
  `Bearer <personal access token>`. See [Authentication](/api-reference/authentication).
</ParamField>

<Note>
  Updating other users requires an administrative role. A token created from a normal
  employee account will not have it.
</Note>

## Body

`application/json`, required. The model is `UserUpdateModel`.

<ParamField body="UserId" type="integer">
  The user to update. Identifiers come from
  [Get all users](/api-reference/users/list) or
  [Get the current user (v2)](/api-reference/users/get-current-v2).
</ParamField>

<Note>
  Because the model is unspecified, assume `PUT` semantics: send the **complete** user,
  not just the fields you are changing. Read the user first, modify the object you got
  back, and send that. A partial body risks clearing the fields you omitted.
</Note>

## Response

`200` — the update succeeded.

<Warning>
  **The body is literal `null`, not the updated user.** The action returns a success result
  that serialises the default of the read model. If you need the post-update state, read
  the user back.

  ```json
  null
  ```
</Warning>

## Errors

| Code | Cause |
| --- | --- |
| `401` | Invalid authentication token, wrong instance, or wrong account. |
| `500` | The update failed. Carries a [`ResponseError`](/api-reference/errors#the-error-body) body. |

<Note>
  There is no documented `400` and no documented `404`. An unknown `UserId` is not
  guaranteed to produce either — confirm the user exists before updating, and read back
  after, rather than inferring success from the status code alone.
</Note>

<Tip>
  This operation **is** idempotent: sending the same payload twice leaves the same end
  state. Safe to retry on a transient failure — unlike
  [Create a user](/api-reference/users/create).
</Tip>
